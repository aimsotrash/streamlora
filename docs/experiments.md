# Experiments

Every number here comes from a stored JSON report under `data/*/runs/`, produced
by `streamlora experiment` or `streamlora lora compare`. The configuration that
produced each one is stored alongside it and hashed into the run id.

---

## Methodology

### Time-aware evaluation, without exception

Nothing is shuffled. An experiment replays one dataset through several **arms**
— each a set of dotted config overrides on a common base — and scores every arm
on the same **held-out chronological tail** after a `train_frac` boundary.

Scoring only the tail is not cosmetic. An earlier version of this harness scored
the whole run, which meant the learned arm was partly judged on its own warm-up
while the baselines — which need none — were not. That biased the comparison
against learning by roughly 30% and is exactly the kind of error that produces a
confidently wrong conclusion.

Where a chronological split is taken directly (`evaluate/splits.py`), training
rows whose *target* time falls inside the next segment are **embargoed**: a
feature window at time *t* forecasting *t+h* has already observed data that a
naive split would place in the test set.

### Arms see identical data

Each arm replays the same in-memory sample list through a fresh pipeline. The
baselines are deterministic, so their metrics must be bit-identical across arms;
the runner **asserts this** and aborts the experiment if they diverge. If the
baselines differ, the arms did not see the same data and no comparison between
them is valid.

### Metrics

MAE is the headline: it is in the signal's own units and robust to the spikes
telemetry is full of. RMSE is reported alongside, because MAE improving while
RMSE worsens means a model got better on average by becoming occasionally
catastrophic. MAPE is **not used** — CPU is legitimately 0.4% on an idle laptop,
where a 2-point error is a 500% "percentage error" and a single idle minute
dominates the day. sMAPE is reported as supporting information only.

Skill is `1 − MAE / MAE_reference` against persistence. Differences are checked
with a Diebold-Mariano test using a Newey-West long-run variance, because
"6.31 vs 6.44" is not a result on 2,000 autocorrelated samples.

Coverage and mean interval width are always reported together: 100% coverage with
an interval spanning 0–100% is worthless, and reporting coverage alone hides it.

### Datasets

**Real telemetry** — 3.3 h, 2,370 samples, 38 signals, from one laptop,
including a 27-minute unplugged
discharge under sustained load (battery 100% → 55%, ~1.4 %/min). This is the only
source of accuracy evidence.

**Synthetic scenarios** — used for correctness, determinism and edge cases, *not*
as evidence about accuracy. They are generated by a process with known structure,
so any model that recovers that structure will look good. What makes them
non-trivial: workload leads CPU; CPU leads temperature through a first-order lag
with a ~90 s time constant (measured lag 12 ticks, r = 0.985); battery is the
integral of power draw; noise is AR(1) with a ~17 s autocorrelation time, because
independent per-tick noise would make short-horizon persistence unbeatable and
long-horizon forecasting impossible.

## 1. Continual adaptation vs a static model

The core question. `static` learns on the chronological prefix then freezes;
the online arms keep learning. Same estimator, same data, same tail.

```bash
bash scripts/run_synthetic_suite.sh data/exp_synthetic 300 core
```

**Online beat static on 34 of 45 scopes; worse on 5.**

### idle → sustained build → idle

| scope | static | best online | online vs static |
|---|---|---|---|
| cpu@5m | 10.522 | 5.870 | **+44.2%** |
| cpu@15m | 22.702 | 14.432 | **+36.4%** |
| cpu@30m | 24.426 | 19.714 | +19.3% |
| mem@5m | 1.397 | 0.933 | +33.2% |
| mem@15m | 4.322 | 2.454 | **+43.2%** |
| battery@5m | 0.006 | 0.001 | +92.2% |

*8 scopes better, 0 worse.*

### permanent regime change

| scope | static | best online | online vs static |
|---|---|---|---|
| cpu@5m | 11.372 | 9.282 | +18.4% |
| cpu@15m | 12.541 | 12.331 | +1.7% |
| mem@5m | 1.394 | 1.362 | +2.3% |
| battery@5m | 0.009 | 0.001 | +84.8% |

*6 better, 1 worse.*

### discharge → charge

| scope | static | best online | online vs static |
|---|---|---|---|
| battery@5m | 3.323 | 1.954 | **+41.2%** |
| battery@15m | 9.878 | 7.511 | +24.0% |
| cpu@5m | 5.636 | 4.784 | +15.1% |
| mem@5m | 0.324 | 0.276 | +15.0% |

*9 better, 0 worse.*

### gappy idle — 20% sample dropout

| scope | static | best online | online vs static |
|---|---|---|---|
| cpu@30m | 3.349 | 2.454 | +26.7% |
| cpu@15m | 2.401 | 1.857 | +22.6% |
| mem@5m | 0.347 | 0.254 | +27.0% |

*6 better, 1 worse. Adaptation still helps with a fifth of samples missing.*

### spike_burst — where adaptation loses

| scope | static | best online | online vs static |
|---|---|---|---|
| cpu@5m | 3.698 | 4.351 | **−17.7%** |
| cpu@15m | 3.638 | 4.471 | −22.9% |
| mem@30m | 0.266 | 0.241 | +9.4% |

*5 better, 3 worse.*

This scenario is **stationary**: the same spike pattern repeats for five hours.
A model trained on the first half is already correct for the second, and every
further adaptation is a selection event against a finite gate window that adds
variance without adding information. This is the correct result, and it is the
argument for drift-triggered rather than unconditional adaptation.

## 2. Learned model vs baselines

The number that decides whether any of this was worth building.

### On real telemetry

3.3 h, 2,370 samples, including a 27-minute unplugged discharge. Core ablation,
metrics on the held-out chronological tail:

```bash
streamlora experiment --dataset file:data/real_telemetry.jsonl --suite core
```

| scope | persistence | EWMA | moving avg | linear trend | best learned | (arm) |
|---|---|---|---|---|---|---|
| cpu@5m | 10.063 | **9.387** | 9.843 | 12.583 | 9.658 | static |
| cpu@15m | 15.417 | 14.950 | 15.277 | 20.434 | **14.637** | online_periodic_drift |
| cpu@30m | 21.863 | 20.864 | 20.864 | 28.899 | **20.710** | static |
| mem@5m | **5.142** | 5.606 | 5.937 | 7.861 | 5.269 | online_periodic |
| mem@15m | 9.139 | 9.191 | 9.345 | 16.013 | **8.721** | online_periodic_drift |
| mem@30m | 11.365 | 10.840 | 10.813 | 26.807 | **10.112** | static |
| battery@5m | 1.990 | 2.613 | 2.816 | **0.482** | 1.974 | online_drift |
| battery@15m | 4.865 | 5.219 | 5.333 | **2.377** | 4.865 | online_periodic |

Read honestly, this is a **more modest result than the synthetic scenarios**:

- The learned model takes **4 of 8 comparable scopes**, and its wins are small
  (+2.1% at cpu@15m, +4.6% at mem@15m, +6.5% at mem@30m against the best
  baseline). At the 5-minute horizon the baselines win on both CPU and memory.
- **Linear extrapolation dominates battery on real hardware too**, exactly as it
  did in simulation: 0.482 against 1.974 at five minutes, a 4× gap. Having now
  measured this on a real 100% → 55% discharge rather than a generated one, the
  conclusion stands: battery should be served by the physics baseline.
- **Online vs static is 3–3 on real data**, against 34–5 on the synthetic drift
  scenarios. Adaptation wins clearly at mem@5m (+24.9%) and loses at cpu@30m
  (−9.0%) and mem@30m (−15.1%). The most likely explanation is that 3.3 h is
  simply not enough for the online arm to accumulate an advantage, and the single
  large regime change in this recording (the unplug) sits close to the split.
  This is the data limitation in `docs/limitations.md`, showing up in the numbers.

### A sample-size artefact worth recording

The first run of this experiment reported `battery@30m` MAE of **43.99** for one
arm against 6.53 for every other — an apparent catastrophic failure. It was not.
That arm had **7** resolved predictions at that scope against ~1198 for the
others, and all seven straddled the moment the charger came out: the model
predicted persistence (correct for a battery that had been flat at 100% for three
hours), and the battery then fell 44 points in thirty minutes.

The model was fine; the *table* was wrong, because it showed a single `n` column
and implied the arms were comparable. Both the report table and the summariser
now print the per-arm sample range and flag any row where the counts differ by
more than 2×, and the online-vs-static comparison refuses to compute a percentage
for such rows. A number that looks like a disaster is worth chasing down before
writing it up.

### Where the learned model wins outright

On `spike_burst`, which has genuine repeating structure, and on `idle_to_build`
at the short horizon:

| dataset | scope | best baseline | learned | skill |
|---|---|---|---|---|
| spike_burst | cpu@5m | 4.513 (persistence) | **3.698** | **+18.1%** (+84% vs EWMA) |
| idle_to_build | cpu@5m | 6.139 (EWMA) | **5.870** | **+4.4%** |
| idle_to_build | mem@5m | 0.942 (persistence) | **0.933** | +0.9% |
| permanent change | mem@5m | 1.387 (persistence) | **1.362** | +1.8% |

### Where a baseline dominates and nothing closed the gap

`discharge_then_charge`, battery:

| scope | linear trend | best learned | gap |
|---|---|---|---|
| battery@5m | **0.386** | 1.954 | 5.1× |
| battery@15m | **2.188** | 7.511 | 3.4× |

State of charge is the integral of power draw, so extrapolating the observed
discharge rate is close to optimal. No configuration tried closed this.

The correct engineering conclusion is that battery should be served by the
linear-trend baseline rather than by the learned model. The system makes that
visible — every metric is reported per (signal, horizon) with the winning arm
named, and the promotion gate records the best baseline's MAE alongside the
candidate's — but it does **not** currently switch automatically. Automatic
per-scope arm selection would need its own hysteresis and evaluation to avoid
flapping between arms on noise, and shipping it untested would be exactly the
kind of unmeasured claim this project is trying to avoid. It is listed as future
work.

## 3. Design ablations

```bash
streamlora experiment --dataset scenario:permanent_regime_change --suite design
```

All four arms on `permanent_regime_change`, held-out tail:

| scope | best baseline | default | no_trust_region | trust_region_correction | no_baseline_features |
|---|---|---|---|---|---|
| cpu@5m | 8.936 (ewma) | **9.579** | 16.871 | 9.984 | 9.676 |
| cpu@15m | 11.059 (ewma) | 12.331 | 19.319 | **11.724** | 12.345 |
| cpu@30m | 14.611 (ewma) | 16.446 | 33.206 | **15.595** | 15.991 |
| mem@5m | 1.387 (persistence) | **1.362** | 4.038 | 1.671 | 1.411 |
| mem@15m | 3.501 (persistence) | **3.567** | 6.779 | 3.849 | 3.622 |
| mem@30m | 6.659 (persistence) | **6.848** | 10.466 | 7.270 | 6.887 |

| arm | promoted | rejected | rolled back |
|---|---|---|---|
| default | 124 | 106 | 9 |
| no_trust_region | 170 | 60 | **16** |
| trust_region_correction | 165 | 65 | 14 |
| no_baseline_features | 144 | 86 | 10 |

### The trust region is the single largest correctness fix

Without it the model is **1.8–2.9× worse on every scope** (cpu@30m: 33.2 vs
16.4). Eighty small coefficients pushed the same way sum to a huge correction,
and a linear model asked to extrapolate does exactly that. The rollback count
tells the same story from another angle: an unshrunk model keeps producing
versions that look acceptable on a 120-sample gate and then fail in production
(16 rollbacks vs 9).

### The variant I expected to win, and did not

`trust_region_correction` spares the intercept and the baseline inputs, shrinking
only the telemetry-derived block, so the fallback is the learned baseline blend
rather than persistence. That *sounds* strictly better — persistence is often the
worst baseline.

It takes 2 of 6 scopes (both long-horizon CPU) and loses the other four,
decisively on memory (1.671 vs 1.362 at 5 min). The baseline inputs are
volatility-normalised too, so on an unfamiliar input they are large as well, and
leaving their coefficients un-shrunk lets the "safe" block extrapolate just as
badly. The default follows the measurement; the variant is kept as an arm because
the long-horizon CPU result suggests the right choice may be per-signal rather
than global.

### Baselines as inputs help, but barely

`no_baseline_features` loses on 5 of 6 scopes — and by margins that are almost
always under 1% (12.331 vs 12.345 at cpu@15m). At cpu@30m it actually wins
(15.991 vs 16.446). The stack is a sound design property — zero weights reproduce
persistence, one unit coefficient reproduces any baseline — but on this data it
is not what makes the model work. The trust region is.

### Regime-conditioned models lose to regime features

```bash
streamlora experiment --dataset scenario:permanent_regime_change --suite regime
```

`per_regime` fits a separate model per workload regime instead of feeding the
regime as a one-hot feature.

| scope | regime as a feature | separate model per regime |
|---|---|---|
| cpu@5m | **9.579** | 9.662 |
| cpu@15m | **12.331** | 12.446 |
| cpu@30m | **16.446** | 16.822 |
| mem@5m | **1.362** | 1.450 |
| mem@15m | **3.567** | 4.149 |
| mem@30m | **6.848** | 9.111 |

Worse on **all six scopes**, and by a widening margin at long horizons where each
per-regime model has the least data (33% worse at mem@30m). This is data
fragmentation: splitting a bounded online memory across seven regimes leaves each
model with too few examples to estimate ~80 coefficients. Sharing one model and
letting the one-hot shift the intercept keeps all the data in one place.

It also promoted *more* (168 vs 124) while rolling back less (7 vs 9), which is
what an under-fitted model looks like from the gate's perspective: its candidates
are noisy but rarely catastrophic.

The regime label still earns its place — it slices every metric, drives the
explanations, and routes drift alarms — but as an *input*, not a partition.

## 4. The safety machinery

```bash
streamlora experiment --dataset scenario:idle_to_build --suite safety
```

`online_no_gate` promotes every candidate unconditionally. On
`permanent_regime_change`, held-out tail:

| scope | gated (default) | no gate |
|---|---|---|
| cpu@5m | **9.579** | 10.723 |
| cpu@15m | **12.331** | 13.828 |
| cpu@30m | **16.446** | 17.685 |
| mem@5m | **1.362** | 1.407 |
| mem@15m | **3.567** | 3.673 |
| mem@30m | **6.848** | 6.886 |

| arm | promoted | rejected | rolled back |
|---|---|---|---|
| gated (default) | 124 | 106 (46%) | **9** |
| no gate | 231 | 0 | **20** |

The gate wins on **all six scopes**, rejects **46% of candidates**, and — the
number that matters most — halves production rollbacks. Without it, bad versions
reach production and the regression watch has to clean up after them, which means
users see the bad forecasts in between.

Note also that *rejection is the normal case*, not a failure mode: a pipeline
that only ever promotes is an unconditional update with extra logging.

On real telemetry (3.3 h, four arms) the full pipeline produced **306
promotions, 132 rejections and 35 rollbacks**. The rejections break down as 84
`hard_reject_worse` and 48 `worse_than_tolerance`. A representative rollback:

```
rolled back: battery.percent@900 (regression_watch)  MAE 6.088 → 18.487
```

That version passed the gate on 120 held-out samples and was 3× worse in
production. The gate alone would have kept it; the regression watch reverted it.
This is the difference between a gate and a guarantee.

### The ratchet — the most instructive failure in the project

The gate originally used `gate_tolerance = 0.02`, on the reasoning that admitting
statistically neutral updates lets the model track slow drift. It does. It also
permits every adaptation to be 2% worse than the last, and over the ~200
adaptations a multi-hour run produces, that compounds:

```
(1.02) ^ 200  ≈  52×
```

Measured skill was **negative on every scope** until the tolerance was set to
zero. Tracking drift is the forgetting factor's job, not the gate's.

Two related fixes came from the same investigation: adapting every 60 outcomes
overfits the gate window (240 is the default), and routing every feature-shift
alarm to all nine scopes turned 55 drift events into 330 triggers.

## 5. Drift detection

Detector behaviour is asserted directly in `tests/test_drift.py`.

| property | result |
|---|---|
| False alarms, 3,000 stationary samples × 3 seeds | **0** for both Page-Hinkley and ADWIN |
| Detection delay, 4σ sustained shift | 7–11 samples (~1 minute at 5 s) |
| Detection delay, 1σ sustained shift | 25–35 samples |
| False alarms on a constant stream | 0 |
| Feature shift identifies the moved feature | yes, by name and sigma |

**The Hoeffding failure.** ADWIN originally used
`ε = sqrt(ln(4/δ') / 2m)`, correct only for variables bounded in [0, 1]. The
standardised error stream is unbounded, so the bound under-estimates by roughly
3× and produced **11 false alarms in 3,000 samples of pure noise**. Replacing it
with the variance-aware ADWIN2 bound eliminated all of them without hurting
detection delay.

**The zero-variance failure.** A perfectly predicted signal gives a warm-up
standard deviation of exactly 0. With a floor of 1e-6, the next error of 1e-4
becomes a 100-sigma event. The floor is now set in error units
(`max(std, 1e-3, 0.01·|mean|)`).

## 6. Uncertainty calibration

| condition | nominal | measured |
|---|---|---|
| Stationary, α = 0.10 | 90% | **90.1%** |
| Stationary, α = 0.05 | 95% | 95.4% |
| Stationary, α = 0.20 | 80% | 79.8% |
| Immediately after a 6× variance shift | 90% | 89.0% |
| Recovered, 500 samples later | 90% | 89.9% |

On 3.3 h of real telemetry (cpu.util_pct, the `online_periodic_drift` arm):

| horizon | nominal | measured | n | mean width |
|---|---|---|---|---|
| +5 min | 0.90 | 0.84 | 1946 | 31.7 |
| +15 min | 0.90 | 0.77 | 1576 | 32.3 |
| +30 min | 0.90 | 0.58 | 1003 | 22.8 |

Coverage degrades badly with horizon. Two causes, and both are real: the residual
pool at long horizons is small on a short run, and the adaptive quantile has less
time to converge when each observation takes 30 minutes to resolve. The dashboard
reports coverage next to interval width so this is visible rather than implied —
the +30 min intervals are *narrower* than the +5 min ones while covering far
less, which is exactly the miscalibration to look for.

The guarantee is long-run *average* coverage, not conditional coverage.

## 7. Language layer

```bash
streamlora lora build-data --examples 400
streamlora lora compare
```

**Stated limitation, first.** There is no corpus of human-written explanations of
this laptop's telemetry, so targets are rendered by the deterministic template
renderer under an explicit persona. This experiment measures whether an
adaptation mechanism can acquire a *specified* style-and-grounding function, and
at what cost relative to the alternatives. It does **not** measure whether people
prefer the output; that needs human labels this project does not have.

What keeps the task from being string memorisation: evidence packs are drawn from
many different times, regimes and questions; the renderer paraphrases (asserted
in the tests); and the split is chronological.

Arms: `template` (no model, the correctness floor), `base` (no personalisation),
`persona_prompt` (preferences in the prompt on every request), `fewshot`
(preferences plus worked examples), `lora` (adapter, nothing added to the
prompt), `full_ft` (all parameters).

### Results

83 training / 36 held-out examples, built from the 3.3 h real telemetry dataset,
split chronologically. Base model SmolLM2-135M-Instruct.

| arm | eval loss | ppl | grounded | fully grounded | style | fully compliant | prompt tok | train s | trainable params | artifact |
|---|---|---|---|---|---|---|---|---|---|---|
| template | – | – | **0.950** | **0.78** | **1.000** | **1.00** | – | – | – | – |
| base | 2.664 | 14.36 | 0.819 | 0.44 | 0.893 | 0.69 | 606 | – | – | – |
| persona_prompt | 2.651 | 14.17 | 0.818 | 0.50 | 0.907 | 0.78 | 636 | – | – | – |
| fewshot | 2.651 | 14.17 | 0.528 | 0.03 | **1.000** | **1.00** | 640 | – | – | – |
| **lora** | **0.635** | **1.89** | 0.742 | 0.44 | 0.898 | 0.72 | 606 | 482 | **1,843,200 (1.4%)** | **7.1 MB** |
| full_ft | **0.177** | **1.19** | – | – | – | – | – | 1103 | 134,515,008 (100%) | 513 MB |

Both trained arms ran on CPU, from the same starting loss (2.6648), so the cost
comparison is device-consistent. LoRA ran at batch 1 after an out-of-memory
retry and full fine-tuning at batch 4, so LoRA's wall-clock advantage is
understated: it did **166 steps in 482 s** against full fine-tuning's **42 steps
in 1103 s** — roughly **10× cheaper per step**. `full_ft` has no generation
metrics because its weights are deliberately not persisted; that arm exists to
measure cost.

**What this supports.**

1. **The low-rank update does the job the prompt cannot.** Putting the persona in
   the prompt moved held-out loss by 0.5% (2.664 → 2.651). The adapter moved it
   by **76%** (2.664 → 0.635, perplexity 14.4 → 1.9) — and it does so with the
   persona *removed* from the prompt, so it is 30 tokens cheaper per request,
   forever.
2. **LoRA is far cheaper than full fine-tuning for most of the benefit.** 1.4% of
   parameters, a 7 MB artefact against 513 MB, and ~10× less compute per step.
   Full fine-tuning does reach a lower loss (0.177 vs 0.635), so the honest
   statement is that LoRA buys most of the adaptation at a small fraction of the
   cost — not that it matches full fine-tuning.
3. **Adapters attach and detach exactly**, so rollback is correct by
   construction, which full fine-tuning cannot offer at all.

**What this does not support — and two findings that go the other way.**

4. **LoRA did not improve groundedness; it slightly hurt it** (0.819 → 0.742).
   The adapter learned the target *style* and became more willing to produce
   confident numeric prose, without learning to keep the numbers to the ones in
   the evidence. This is the clearest argument for the verifier existing as a
   separate mechanism rather than something a model is trusted to internalise.
5. **Few-shot prompting is actively harmful to grounding.** Style compliance
   reaches 1.00 — the examples teach the format perfectly — but groundedness
   collapses to **0.528**, and only **3%** of answers are free of invented
   numbers. The model copies figures out of the worked examples. A project that
   measured only style would have concluded few-shot was the best arm.
6. **The deterministic renderer still wins the metric that matters most.** It is
   the only arm at 0.95 groundedness and 1.00 style compliance, and it needs no
   model at all. Which is exactly why the service serves it whenever a generation
   fails verification.

The bottom line for the stated hypothesis: **small low-rank updates do
personalise the interaction layer far more efficiently than repeated full
fine-tuning, and far more effectively than prompting — on the style-and-format
objective. They do not fix hallucination, and nothing here suggests they would.**

## Reproducing everything

```bash
# the five synthetic scenarios, core ablation
bash scripts/run_synthetic_suite.sh data/exp_synthetic 300 core

# design and safety ablations
streamlora experiment --dataset scenario:permanent_regime_change --suite design
streamlora experiment --dataset scenario:idle_to_build --suite safety

# on your own telemetry
streamlora collect --minutes 240
streamlora export data/mine.jsonl
streamlora experiment --dataset file:data/mine.jsonl --suite core

# language layer
streamlora lora build-data --examples 400 && streamlora lora compare

# regenerate the tables in this document
python scripts/summarize_experiments.py data/exp_synthetic/runs
```

Reports land in `<data_dir>/runs/<experiment_id>.json` with the full config
embedded. Every metric row is also written to the `metrics` table tagged with the
experiment and arm.
