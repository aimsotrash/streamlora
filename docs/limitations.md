# Limitations

Stated plainly, because several of these bound what the results mean. Ordered by
how much they constrain the conclusions.

## Data

**3.3 hours of real telemetry from one machine.** This is the binding constraint
on every accuracy claim. It is enough to show the pipeline works end to end, to
confirm the battery finding on a real discharge, and to demonstrate that the
learned model wins at longer horizons — but not enough to see diurnal structure,
which is precisely what the time-of-day features exist to exploit. It is also why
online-vs-static is only **3–3 on real data** against **34–5** on the synthetic
drift scenarios: the mechanism works, but three hours with one regime change near
the split cannot demonstrate it. A week of collection would materially change
what can be concluded.

**The discharge was captured under artificial load.** The 27-minute unplugged
trace (100% → 55%, ~1.4 %/min) was recorded while this project's own experiments
were saturating the CPU and GPU. That is a real discharge on real hardware, but
it is a *heavy-load* discharge, not a representative one.

**One hardware configuration.** Every real measurement comes from a single Linux
laptop with a sysfs battery that reports fractional charge. The architecture degrades gracefully elsewhere — psutil
fallbacks, role-mapped thermal sensors, vendor-neutral GPU signal names — but
"degrades gracefully" has only been tested by removing sources, not by running on
a Mac.

## Synthetic scenarios are not accuracy evidence

They are generated by a process with known structure, so any model that recovers
that structure will look good. They are used for correctness, determinism and
edge cases: does the drift detector fire when the regime changes, does replay
reproduce bit-identically, does the system survive a 20% dropout. Every accuracy
claim that matters is measured on recorded real telemetry, and the documents say
which is which.

## Modelling

**The forecaster is linear.** It cannot express "CPU will spike when the build
reaches linking", or any interaction not already encoded in a feature. That
ceiling is real and is the most likely reason EWMA still wins on smooth signals.
Gradient-boosted trees or a small sequence model would probably do better on
accuracy; neither updates incrementally without replay-based retraining or
catastrophic forgetting, which is the trade this project exists to study. The
right next experiment is a Hoeffding tree or an online GBM, to find out whether
the ceiling is the model class or the data.

**The learned model is a correction on top of the baselines**, which have their
forecasts as model inputs. This is good engineering — zero weights reproduce
persistence, one unit coefficient reproduces any baseline — but it changes how
the headline number should be read. "The learned model beat persistence by 11%"
means the correction layer added 11%, not that an independent competitor won.

**Regimes are threshold rules, not learned.** They are seeded from interpretable
thresholds and evaluated per-regime so a useless label is visible, but nothing
discovers them. And the measured result is that regime-*conditioned models* lose
to regime-as-a-feature, so the labels currently earn their place through
interpretability and metric slicing rather than through accuracy.

**Interval coverage is long-run average, not conditional.** Intervals are too
wide when the machine is calm and too narrow in the first minutes of a new
regime. At long horizons on a short run the residual pool is simply too small —
measured coverage was 0.39 at +15 minutes against a nominal 0.90. The dashboard
reports coverage next to interval width so this is visible rather than implied.

## Language layer

**Targets are machine-rendered, not human-written.** There is no corpus of human
explanations of this laptop's telemetry, so the LoRA experiment's targets come
from the deterministic renderer under an explicit persona. It measures whether an
adaptation mechanism can acquire a *specified* style-and-grounding function and
at what cost. It does **not** measure whether anyone prefers the output. Turning
it into a usefulness result needs human labels.

**Groundedness is a numeric-containment check.** Every number in an answer must
appear in the evidence. This catches invented measurements, which is the failure
that matters here — but it cannot catch a fluent sentence that misreads a correct
number ("CPU is falling" when 40 → 60 are both in the evidence). Semantic
faithfulness is unmeasured.

**The base model is 135M parameters.** Chosen so continual adaptation takes
seconds and the full-fine-tune comparison fits on a small laptop GPU. Absolute
answer quality would be higher with a larger model; the relative cost comparison
is the point, and it is what the experiment reports.

**Rule inference is deliberately conservative.** "That's normal for me" parses;
"I only worry when it's above 80" does not, and is kept as context rather than
guessed into a rule. A wrong rule silently changes every future explanation, so
the failure mode is chosen to be "no rule" rather than "wrong rule".

## Engineering

**Single machine, single process, single SQLite file.** Correct for the workload
and an explicit choice, but it means no multi-device history and no concurrent
writers beyond what WAL allows.

**GPU LoRA training needs CPython development headers.** PyTorch's Triton path
shells out to a compiler for a CUDA helper that includes `Python.h`. Without
`python3-devel` / `python3-dev` the arm falls back to CPU automatically and says
so, but the fallback is 10–20× slower.

**`Quality.IMPUTED` is reserved and currently unused.** The normaliser holds
values as `STALE`; feature-level imputation happens in the extractor and is not
per-reading. The enum member is kept rather than removed because quality is
stored as an integer, and renumbering would be a data migration for no benefit.

**No authentication on the API.** It binds `127.0.0.1` and is intended to be
local-only. Exposing it on a network would need auth added first.
